# WipeCode

Rootless-твик (Dopamine, iOS 15–16.6.1). Добавляет в «Настройки» панель, где задаётся
**второй пароль стирания**, не связанный с код-паролем устройства. Если ввести именно его —
выполняется системная «Стереть контент и настройки».

> **Состояние: панель переписана и жёт проверки на устройстве, стирание не подтверждено.**
> Компиляция и доставка через источник проверены. Причина, по которой старая панель не
> показывалась, установлена пробой: тип спецификатора `PSWebView` обслуживает класс
> `PSWebViewController`, а его в процессе Настроек **нет вообще** (`NOT FOUND`), то есть
> инстанцировать панель было нечем. Панель теперь строится твиком самим и не зависит ни от
> перечисления бандлов, ни от приватных классов Настроек. Вызов сброса данных собран по
> подтверждённой сигнатуре, но на реальном устройстве ещё не запускался.

## Установка

Источник для Sileo / Zebra:

```
https://no-recovery.github.io/wipecode
```

Имя репозитория строчными буквами — не украшение. Sileo приводит адрес источника к
нижнему регистру, а адрес project site в GitHub Pages регистрозависим: при
`No-Recovery/WipeCode` Sileo запрашивал `/WipeCode/`, которого не существует, и
показывал 404.

Ставится **один** пакет — `com.vo1dek.wipecode`. Он объявляет `Conflicts`/`Replaces` на
старые `com.vo1dek.wipecode-sb` и `com.vo1dek.wipecode-pref`, поэтому пакетный менеджер
снимет их сам; руками удалять не нужно.

Почему не `raw.githubusercontent.com`: он долго отдавал устаревший `Packages` уже после
того, как ветка уехала вперёд, и в списке оказывались и старая падающая сборка, и новая.
Индекс публикуется через GitHub Pages, он всегда соответствует текущему коммиту.

## Устройство

Один dylib, внедряемый в два процесса. Объединить их в один процесс нельзя:
`FBSSystemService` требует entitlement `com.apple.springboard`, который есть только у
SpringBoard, а панель по определению живёт в Настройках. Поэтому фильтр содержит оба
bundle id, а решает, какая половина запустится, идентификатор процесса.

| | процесс | роль |
|---|---|---|
| одна и та же `WipeCode.dylib` | `com.apple.Preferences` | панель, ввод пароля, HMAC, отправка запроса |
| одна и та же `WipeCode.dylib` | `com.apple.springboard`  | сверка HMAC, вызов сброса данных |

Связь между половинами — Darwin notification (payload не несёт) + файлы в
`/var/mobile/Library/WipeCode` (оба процесса под UID `mobile`).

Darwin notification может отправить любой процесс, поэтому авторизация — не сам факт
уведомления, а HMAC-SHA256 от введённого пароля с персистентной случайной солью.
**Открытый пароль не попадает ни на диск, ни в уведомление** — только 64-символьный дайджест.

### Почему панель больше не `PreferenceBundles`

Классическая схема — бандл в `/var/jb/Library/PreferenceBundles` с `PSWebView` в
`Root.plist` — на этом iOS нерабочая, и это видно из пробы, а не из догадок:

- `PSWebViewController` в процессе Настроек отсутствует; на specifier `PSWebView`
  инстанцировать нечего, поэтому панель не отрисовалась бы даже при перечисленном бандле;
- бандл лежал на диске, `Info.plist` и `Root.plist` парсились, но в списке открытых
  Settings plugin-бандлов не появлялся ни один сторонний.

Поэтому твик добавляет в список Настроек собственную строку и сам пушит свой контроллер с
`WKWebView`. Страница та же (`pane.html`), переехала из
`PreferenceBundles/WipeCode.bundle` в `/var/jb/Library/WipeCode/pane.html` — каталог
`PreferenceBundles` Настройки перечисляют, и туда больше ничего класть не нужно.

## Вызов стирания

`SBDeviceErase` на iOS 15/16 **не существует** — это подтверждено на устройстве. Реальный
путь найден пробой и подтверждён дампом методов:

```
FBSSystemService  +sharedService                      @16@0:8
FBSSystemService  -dataResetWithRequest:completion:   v32@0:8@16@?24
FBSDataResetRequest -initWithMode:options:reason:     @40@0:8q16q24@32
FBSDataResetRequest -mode                             q16@0:8
FBSDataResetRequest -options                          q16@0:8
FBSDataResetRequest -reason                           @16@0:8
```

Запрос строится именно этим инициализатором: `mode` и `options` — `long long`, `reason` —
`NSString`, и все три обязательны, `-new` их не заполняет. Точные значения enum
`mode`/`options` из дампа не читаются — их добирать из настоящего сброса Настроек.

## Что происходит при нажатии «Стереть устройство»

1. Панель показывает нативное поле ввода. Клавиатура и проверка длины берутся из типа
   код-пароля, который SpringBoard публикует в `device.plist`.
2. Показывается обратный отсчёт 5 секунд с кнопкой «Отмена». Запрос не отправляется, пока
   счётчик не дошёл до нуля.
3. В `request.plist` пишется дайджест, отправляется Darwin notification.
4. SpringBoard сверяет дайджест, удаляет `request.plist` (запрос не переигрывается) и
   вызывает сброс данных.

## Сборка

Корень не является пакетом (у него нет `control`), поэтому собирается единственный
subproject. Он самодостаточен: свой `control`, свой фильтр в корне.

```sh
export THEOS=/opt/theos
mkdir -p "$THEOS/packages"
make -C wipecode package FINALPACKAGE=1 THEOS_PACKAGE_SCHEME=rootless \
  THEOS_PACKAGE_DIR="$THEOS/packages"
```


`THEOS_PACKAGE_DIR` обязан быть абсолютным и существовать: `before-package` в Theos
падает с `No rule to make target 'packages'`, если каталога нет. Держать его внутри
`$THEOS` не стоит — кэш CI восстанавливает весь каталог Theos вместе со старыми `.deb`.

Исходники намеренно называются `*.x`, а не `*.m`: Theos прогоняет Logos только по `.x`,
и при расширении `.m` хуки молча не генерируются.

Индекс apt-репозитория собирается отдельно:

```sh
python3 tools/make-repo.py dist packages/*.deb
```

`dist/` коммитится в `main`, а его содержимое публикуется в ветку `gh-pages` силами CI.

## Диагностика

Всё пишется в один файл:

```
/var/mobile/Library/WipeCode/probe.log
```

Probe выполняется **внутри Preferences**, а не из SpringBoard, и это принципиально: классы
`PS*`, на которых живут панели Настроек, в SpringBoard вообще не загружены, поэтому их поиск
оттуда всегда показывал «отсутствуют» — и первые два круга диагностики так и выглядели, будто
у панели нет класса-хозяина. Половина на SpringBoard probe не ведёт.

Проба v1 перечислила классы по угаданным именам и вывела, что `PSWebViewController`
в процессе Настроек **нет**. Проба v2 перестаёт угадывать: вместо «давай поищем класс с
таким именем» она спрашивает у рантайма «какие классы вообще реализуют такой-то селектор»
(`setUserStyleSheet:`, `webView:shouldStartLoadWithRequest:navigationType:`), плюс
перечисляет содержимое `/var/jb/Library/PreferenceBundles` и методы `PSUIPrefsRootController`,
`PSUIPrefsListController`, `PSBundleController`.

Строка в список Настроек добавляется подменой трёх методов таблицы у конкретного класса
списка (`tableView:numberOfRowsInSection:`, `...cellForRowAtIndexPath:`,
`...didSelectRowAtIndexPath:`). Исходные реализации, которые класс наследует, сохраняются и
вызываются для всех остальных строк, так что поведение Настроек не меняется: индекс
собственной строки считается как «число строк, которое сообщили сами Настройки», поэтому
реальные строки не сдвигаются. В лог пишется, в какой класс строка вставлена.

Запуск защищён маркером с номером версии (`[probe] pref done v2`), поэтому после обновления
probe перезапускается сам — вручную удалять лог не нужно. Чтобы прогнать заново на
текущей сборке, достаточно удалить `probe.log`.

Забрать лог: Filza → `/var/mobile/Library/WipeCode/probe.log`.

## Известные ограничения

- **Тип код-пароля не определяется.** `SBAuthenticationManager` на iOS 15/16 нет, панель
  получает `unknown` и показывает обычную буквенно-цифровую клавиатуру. Класс-кандидат ищет
  probe.
- **Запасной путь через `fdesetup` не работает.** На устройстве `/usr/bin/fdesetup` не
  доступен из SpringBoard, а `sudo -n` требует пароль (`требуется указать пароль`,
  код 256). Код оставлен, но выключен; включать его не имеет смысла без sudoers.
- **Значения `mode`/`options` у `FBSDataResetRequest` не подтверждены.** Подпись известна
  точно, а значения enum из неё не читаются; сейчас передаётся 0 в обоих. Если сервис
  отклонит запрос, об этом скажет completion-блок.

## Предупреждение

Стирание необратимо. Проверять надо на устройстве без важных данных: отличить «работает»
от «не работает» без реального стирания нельзя, а таймер отмены — единственная страховка.
